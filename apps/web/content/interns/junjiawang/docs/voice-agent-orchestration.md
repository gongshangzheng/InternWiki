## 一、先讲清楚问题有多痛

### 改造前：业务方要自己当「装配工」

想让一个用户和 AI 语音对话，业务方得**按正确顺序**依次调用 4 个不同的系统：

```mermaid
graph LR
  A[1. 创建 RTC 频道] --> B[2. 给人签 Token]
  B --> C[3. 给 AI 签 Token]
  C --> D[4. 启动 Agent 网关]
  D --> E[5. 会话状态落库]
```

这里的坑在于：

1. **顺序不能错** — 频道还没建就签 Token，Token 是无效的。
2. **appId 必须一致** — RTC 频道属于哪个「应用」，两端 Token 就必须签在同一个 appId 下。错一个字，通话直接连不上。
3. **失败后没人收尸** — 最要命的是第 4 步成功、第 5 步失败的情况。Agent 已经在 RTC 房间里跑起来了，但**数据库里没有这条会话记录**，于是没有任何系统知道要去停掉它。这个 AI 实例就一直挂在房间里，持续消耗 GPU 算力和大模型 Token。

用 STAR 来说，这就是 **Situation（情境）**：多系统编排易错、且失败路径会漏资源。

**Task（任务）**：把分散的多系统调用收敛为单一原子接口，并保证「启动即可追踪、结束必被回收」。

## 二、Action：我具体做了什么

### 2.1 设计单一入口 `POST /session/start-agent`

对外只暴露一个 JSON 请求体，服务端内部统一分配**四元标识**：

| 标识 | 作用 |
|------|------|
| `sessionId` | 会话唯一 ID，后续所有状态流转都靠它 |
| `channelId` | RTC 频道 ID（语音房间号） |
| `webUserId` | 真人在房间里的身份 |
| `agentUserId` | AI 在房间里的身份 |

四个 ID 都由服务端生成，并带**唯一性兜底重试**（生成后校验冲突，冲突则重新生成）。业务方完全不需要理解这四个 ID 之间的约束关系。

### 2.2 抽象 `AgentGatewayFacade` 门面层

这里解决的是一个很实际的问题：Agent 网关有两条通路（HTTP 和 HSF RPC），如果两条通路各写一套请求体组装代码，**迟早会漂移**——改了 HTTP 忘了改 HSF，线上就出诡异 bug。

我的做法是抽出一个统一的 `buildStartAgentBody()` 方法负责组装协议报文，两条通路共用它。效果是：

- **HTTP 与 HSF 两条通路的请求体结构 100% 一致**
- 通路切换只需改一个配置项 `agent.gateway.transport`，**零代码改造**

> 这是**门面模式（Facade）**的典型用法：把「多种底层调用方式」的差异藏在一个统一入口后面，上层代码完全无感。

### 2.3 实现多通路动态路由

平台要支持 4 种形态的通话，它们走的底层链路完全不同：

| 形态 | 走的通路 | 为什么不一样 |
|------|----------|--------------|
| 三段式（ASR-LLM-TTS） | EA 边缘通路 | 边缘节点离用户近，降低首字延迟 |
| 一段式 S2S | 网关 HSF 通路 | 需要 RPC 的强类型契约与内网性能 |
| 数字人模式 | 动态切换至专用 RTC 应用 | 数字人要推视频流，用的是另一套 RTC appId |
| SIP 电话外呼 | 网关下发 SIP 参数 | 详见总览的「补充工程贡献」 |

### 2.4 最巧的一处设计：把状态编进 ID 前缀

**数字人 appId 错配**这个线上事故我印象最深。

问题是这样的：数字人模式启动时用的是**专用 RTC appId**，但 stop 接口只拿到一个 `sessionId`，它**不知道**这次通话当初是用哪个 appId 启的。用默认 appId 去停，网关找不到任务，于是——**智能体停不掉**。

常规解法是加一个数据库字段记录 appId。但当时表结构变更需要走流程、有发布窗口。我用了另一个办法：

**把数字人标记编码进 `agentUserId` 的前缀（`ai-dh-`）。**

```
普通模式:   agentUserId = ai-xxxxxx
数字人模式: agentUserId = ai-dh-xxxxxx
                          ^^^ 这三个字符就是标记
```

stop 侧读到 `agentUserId` 以 `ai-dh-` 开头，就知道要用数字人专用 appId。**零表结构变更**解决了问题。

> 这个设计的取舍：优点是零成本、立即可用；缺点是把语义耦合进了 ID 格式，属于「隐式约定」。所以我在代码里用常量集中定义了这个前缀并加了注释，避免后人踩坑。如果重来一次、且没有发布窗口限制，我会倾向加显式字段。

### 2.5 攻克容器出站 TCP 被拦截

上线联调时遇到一个非常难定位的问题：本地跑得好好的 HTTP 直连网关，**部署到 Pandora 容器里就报 `Network is unreachable`**。

排查结论：Pandora 容器的出站 TCP 连接被安全策略拦截了，应用层无论怎么改超时、改重试都没用。

**我的处理**：把主通路从 HTTP 直连**重构为 HSF RPC 调用**（走内网服务发现，不受出站拦截影响），同时**保留 HTTP 通路作为本地联调与降级备份**。

这一步能低成本完成，正是因为 2.2 已经抽了门面层——请求体组装逻辑完全复用，只换了传输层。

## 三、Result：结果

| 指标 | 改造前 | 改造后 |
|------|--------|--------|
| 业务方接入代码量 | 约 200 行多系统编排 | **1 次 HTTP 调用** |
| 接入周期 | 2 天 | **15 分钟** |
| 通路切换成本 | 改代码 + 发布 | **改 1 个配置项，零代码** |
| 新通路接入成本 | — | 降低约 **70%** |
| 数字人智能体停止成功率 | 不足 **60%** | **100%** |

数字人 appId 问题修复后，彻底消除了实例空跑造成的算力浪费。

## 四、面试追问预案

**Q：为什么要抽门面层？直接写两个方法不行吗？**

行，但会漂移。协议报文有 50+ 字段，两套组装逻辑意味着每次加字段都要改两处，漏一处就是线上 bug，而且这类 bug 只在切换通路时才暴露，非常难测。门面层的本质是**把「唯一正确的组装逻辑」变成单点**，代价只是多一层间接调用。

**Q：把语义编进 ID 前缀不是很脏吗？**

确实是权衡。当时的约束是表结构变更要等发布窗口，而线上正在因为这个问题「停不掉智能体」持续烧钱。我选择先用零变更方案止血，同时把前缀定义为常量、加注释、在设计文档里记录。如果没有时间压力，加显式字段是更干净的做法。**我能说清为什么当时选它，也能说清它的代价。**

**Q：`Network is unreachable` 你是怎么定位到是容器策略而不是代码问题的？**

关键是做了对比实验：同一份代码在本地能通、在容器里不通，说明不是代码逻辑问题；容器内 telnet 目标端口也不通，说明不是应用层的事；而容器内访问内网 HSF 服务正常，说明网络本身通、是**出站方向的 TCP 被拦**。定位到这一层，方案自然就是换传输协议而不是继续调应用参数。

**Q：四元 ID 的唯一性兜底重试，会不会有并发问题？**

会。所以重试不是纯客户端生成后重试，而是依赖存储层的唯一约束——插入冲突才重试，靠数据库保证最终唯一，而不是靠「先查再插」（那样有竞态）。这和我在 [鉴权篇](docs/voice-agent-auth.md) 里用 Redis Lua 保证原子消费是同一个思路：**并发安全必须靠原子操作，不能靠检查顺序。**
