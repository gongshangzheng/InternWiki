## 一、架构概览

## 二、抖动治理

### 2.1 呲呲声：发布节奏慢于实时 5-8%

**现象**：浏览器端听感有周期性呲呲声。**取证**：发布节奏慢于实时 5-8%，浏览器 jitter buffer 持续变薄，触发 NetEQ concealment 隐藏——呲呲声是隐藏操作的伪影。

两个根因，两个解法：

1. **NVENC 流编码器每段死等 200ms tail grace**——改为 shortfall==1 即返回 + deficit 记账（错过的量欠着，下段补）
2. **每段相对锚定**——~2% 的每段超出逐段累积。改为**绝对网格 deadline** + 300ms 重锚定护栏（防时钟漂移拉偏）

| 指标 | 治理前 | 治理后 |
|------|--------|--------|
| cadence | 1.06× | **1.000（稳态）** |
| concealment | 3% | **0** |
| TTFF | 2.2s | **~1s** |

### 2.2 段间爆破音

每 200ms 段重建一次 Opus encoder，编码器内部状态归零导致 19733 LSB 的解码阶跃——听感是"噗"。解法：**per-peer 持久 encoder 复用**，一段用完不销毁。

### 2.3 僵尸会话

浏览器直接断开（关标签页）不清理：GPU 滞留 ~9GB、10 分钟内 173 次 resync。解法三件套：terminal 状态补 Delete 消息 + idle 驱逐挂清理 + peer 30s 看门狗。30s 回收、GPU 归零。

### 2.4 间歇卡顿：取证方法论（本节最值钱）

**现象**：fps 25→12-14 的间歇性掉帧，复现不稳定。

**取证过程**：排除代码回归（同码重跑正常时段无问题）→ 对齐 GPU 利用率曲线 → 定位为 **GPU0 同租户训练任务争用**，非本系统 bug。

**方法论**：性能问题先取证（录制、复现、对照），再区分"代码问题 / 环境问题 / 资源争用"三类。环境问题改代码是白费。

## 三、速度优化

| 优化 | 问题 → 方案 | 效果 |
|------|------------|------|
| alignment batch 化 | 逐帧 20 次 GPU 同步 → batch=10 | paste p95 4750→**52.7ms**（-98.9%） |
| 全 GPU 帧管线 | GPU 去归一化、uint8 H2D、采样网格缓存、pinned D2H、去全量 concat | paste p95 67.3→**12.7ms**，RTF 0.698→**0.588**，TTFF 1.39→**1.18s** |
| 人脸 ROI warp | 720p 全画布 warp 15ms/帧 → 只 warp 人脸 ROI | 恢复实时 |
| 软编码 → NVENC H.264 | VP8 软编 → ffmpeg NVENC 子进程（探测失败自动回退软编） | 同耗时钟像素吞吐 **3.3×**，浏览器硬解；预热 663→445ms |
| inference 按需生命周期 | 常驻进程 → 空闲 3 分钟停进程 | GPU 归 0（empty_cache 还不了 CUDA context，只有退进程） |

## 四、负结果档案

失败的优化同样有档案（防重蹈 + 选型依据）：

| 尝试 | 结果 | 原因 |
|------|------|------|
| fp16 / DDIM 少步 | 只降 RTF 不提 fps | GPU 饱和——fps 卡在显存带宽/拷贝，不在计算 |
| ditto GPU putback 及若干微优化 | 零收益 | 默认 CUDA 流串行，微优化被同步点淹没 |
| config 降帧 25→20 | **反而更抖** | fps 低于消费速率，buffer 消耗快于补充 |
| turn-audio-flush | 弃做 | RTF<1 后积压形态搬家，问题没消失只是换位置 |
| 换轮 TTFF 2.18s | 仍在 | 待 timeline 跳播方案 |

**负结果的规律**：优化前先定位瓶颈类型（计算/带宽/同步/调度）——类型不对，手段再花哨也是零收益。

## 面试追问预案

**Q：呲呲声问题为什么这么难查？**

因为症状在**播放端**（浏览器），根因在**发布端**（服务器节奏），中间隔着网络和 jitter buffer。听起来像音频 bug、像网络丢包、像编码问题——都不是。突破口是把"节奏"量化成 cadence 指标（发布时长/真实时长）：1.06× 意味着每秒慢 60ms，jitter buffer 必然被抽干。这类跨端问题必须先建**可观测指标**再谈修复，否则就是玄学调试。

**Q：绝对网格 deadline 和相对锚定，为什么前者对？**

相对锚定是"每段从上一段结束时刻起算 200ms"——每段的误差会**累积**进下一段的基准。绝对网格是"所有段对齐到全局时钟的 200ms 整数倍刻度"——单段超时只影响自己，不污染后续段的基准。但纯绝对网格有风险：时钟源漂移会让 deadline 和真实时间慢慢脱钩，所以要加 300ms 重锚定护栏。本质是把误差传播从"链式累积"改成"独立有界"。

**Q：负结果里"降帧反而更抖"怎么解释？**

直觉是"帧少了计算量小了应该更流畅"。但实时流媒体的本质是**供需平衡**：消费端固定按 25fps 播，供给降到 20fps 后 buffer 每秒净消耗 5 帧——buffer 变薄触发 concealment，比计算跟不上更抖。教训：实时系统的参数要按"消费端需求"定，不能按"生产端省力"定。这类反直觉结论只有实测才能发现，也是我们坚持 A/B 门槛的原因。
