## 一、指标地图：问题 → 指标

所有指标按"回答的问题"组织（40+ 项，Tier 1 基础 + Tier 2 THEval 衍生）：

| 问题 | 指标 | 备注 |
|------|------|------|
| 嘴型和声音对得上吗 | Sync-C / Sync-D | SyncNet 双流余弦；经验值：自然视频 >5、好生成 >3、不同步 <2 |
| 生成的人和参考是同一人吗 | CSIM | ArcFace 余弦；模板统一中间帧 |
| 像素级有多接近 | PSNR / SSIM | 有参，需 GT |
| 人眼看起来质量好吗 | LPIPS / TOPIQ-FR | 感知类，有参 |
| 不需要参考图质量如何 | NR-IQA 族（musiq_koniq、topiq_nr、arniqa、liqe…） | 整帧 / 人脸裁剪 / 嘴唇裁剪三档 |
| 时间长了会变差吗 | CSIM-drift / LPIPS-drift / Dino-S | 长视频漂移 |
| 运动自然吗 | SID / flow_smoothness / motion_magnitude | 运动多样性与抖动 |
| 表情如何 | expression_nr / expression_cls | 笑容强度等 |
| 跑得快吗占多少资源 | FPS / RTF / VRAM / GPU-Util / Throughput / Latency P50/P95/P99 | 效率族 |
| 分布有多接近 | FID | 生成帧 vs GT 帧分布 |
| 动态细节（THEval） | lip_dynamics / silent_lip_stability / theval_lip_sync 等 | 静默段唇部稳定、嘴开合与音频 RMS 同步 |

**组织原则**：引入任何指标前先写清它回答什么问题、在什么轨道上适用（`applies_to` 绑定——cross_identity / listening 轨道无 GT，有参指标必须排除）。

## 二、口径的坑（演进史）

这部分是教训，比指标本身更值钱。

### 2.1 指标只在人脸裁剪视频上算

pasteback 贴回的全帧视频**不参与任何指标**。两层裁剪共存：

- 输入侧：统一人脸构图契约（face_crop，crop_coeff=1.9，输入侧裁一次）
- 指标级：PSNR/SSIM 等构造函数自带 face_crop_mode（指标级二次裁剪）

原因：不同模型的 pasteback 构图不同，全帧算 PSNR 会把"贴回位置差异"算成画质差异。

### 2.2 勘误：LPIPS / TOPIQ-FR 并非不受裁剪影响

旧文档曾断言这两个指标不受 face_crop_mode 影响——查代码发现构造函数默认值就是 face_margin，**同样在做二次裁剪**。教训：口径断言要对着代码验证，不能凭印象写文档。

### 2.3 speed-run 打分口径定稿

- SyncNet v2 + 恢复人脸检测（曾走过 ≤512px 整帧 resize 捷径，导致打分失真）
- 身份模板统一**中间帧**（对齐 guanmu 生成原理）
- 共用裁剪框：各模型输出裁成同构图 face.mp4，构图逐像素一致，指标才可比

### 2.4 与参考实现逐指标对齐

和 guanmu 参考实现对照：sync 族 corr=1.000、csim 冒烟逐像素 diff=0、musiq_koniq 全帧口径对齐。**指标实现的可信度靠对照锚定**，不是靠"代码跑通了"。

## 三、指标与实际问题的映射案例

### 案例 1：怀疑长视频身份漂移

CSIM-drift 曲线定位 → 曲线下降但不知道机制 → 引出 latent 膜长/夹角假设检验（见 [Avatar Forcing 微调实践](../微调与实践/Avatar%20Forcing%20微调实践.md)）——**指标发现问题，实验定位机制，治理解决问题**。

### 案例 2：唇同步分数可疑地高

Wav2Lip 在我们的评测里 LSE 得分最高——但它是换嘴算法，理论上表现上限有限。判定：结果可疑，需复验。教训：**单一指标会骗人**，异常高分和异常低分一样要怀疑；交叉验证（换指标族、人工抽查）后才能采信。

### 案例 3：3DGS 无背景算法的 PSNR 不公平

3DGS 类算法输出透明背景，与 GT 的实背景算 PSNR 天然吃亏——对人脸区域做 matting 前置后再算。教训：**指标可比的前提是输入同构**，算法族的输出形态差异要先归一再评测。

## 四、轨道设计

5 条评测轨道（standard / cross_identity / listening / long_run / stress_test），指标按 `applies_to` 绑定轨道。无 GT 轨道（cross_identity、listening）只能用无参指标——指标体系在一开始就要为"没有 GT 的场景"留位置。

## 面试追问预案

**Q：为什么坚持"指标只在人脸裁剪视频上算"？全帧算不是更贴近用户观感吗？**

可比性优先。不同模型的 pasteback（贴回原视频）构图策略不同：有的贴得偏上、有的缩放不同——全帧 PSNR/SSIM 会把构图差异算成画质差异，模型 A 比 B 差可能只是因为它贴得偏了 20 像素。人脸裁剪 + 共用裁剪框把"贴回策略"这个无关变量从评测里剔掉，测的才是生成本身。用户观感由 NR-IQA 整帧指标单独覆盖，两类问题分开测。

**Q：FPS 和 RTF 都测，冗余吗？**

不冗余，它们回答不同问题。FPS 是"单位时间出多少帧"（渲染吞吐），RTF 是"处理一段音视频的耗时 / 该段真实时长"（能否实时）。离线批量生成只关心 FPS 不太关心 RTF；实时流式系统 RTF>1 就意味着积压——CyberVerse 的抖动治理正是从 cadence（RTF 的发布侧视角）入手的（见 [CyberVerse 工程专题](CyberVerse%20工程专题.md)）。另外论文 FPS ≠ 产品 SLA：模型单独跑的 FPS 不含级联排队，产品侧要单独压测（Throughput / Latency-P95/P99 就是为此引入）。

**Q：指标体系怎么防止越加越臃肿？**

三条纪律。① 每个指标注册时写清"回答什么问题"——说不出来的不收；② 轨道绑定（applies_to）——与轨道无关的指标不跑，报告只呈现相关项；③ 有进有出——指标被更可信的实现替代时旧口径归档勘误（如 speed-run 打分口径定稿时旧值明确标注不可比）。40+ 项听起来多，但按问题分组后每个问题域只有 2-5 个核心指标，其余是变体（人脸/嘴唇裁剪 × 整帧三档）。
