## 一、项目一句话概述

**独立主导设计并落地一套多模态 RAG Agent 编排与评测平台**，通过「注册中心 + 策略模式」实现检索、重排、生成三段式 Agent 工作流的插件化编排，支撑 **16 个检索器 × 7 个重排器 × 3 个生成器 × 13 个数据集（文本/图像/文档/视频）** 的任意组合评测，累计沉淀 **279 组实验报告**，为多模态 RAG 技术选型提供唯一可信数据源。

**技术栈**：Python 3.10 / PyTorch / Transformers / Pydantic / 装饰器注册中心 / 策略模式 / 多进程数据并行 / ThreadPoolExecutor 并发 / numpy memmap / DashScope & Gemini & Doubao 多云 API / structlog + rich 可观测性 / Matplotlib 可视化

**工程规模**：核心代码约 **4.2 万行**（`mmrag_eval` 包 + `scripts` + `tests`），单机 8 卡 GPU 环境，最长单次索引任务连续运行 **89 小时**。

## 二、核心技术亮点（STAR）

### 亮点一：设计插件化 Agent 编排内核，将新能力接入成本从「改动多处」降为「一文件一装饰器」

- **S｜情境**：团队需横向评测数十种多模态 RAG 方案，早期实现里检索器、重排器、生成器与流程控制强耦合，每接一个新模型都要改动配置解析、流程编排、指标计算多处代码，且流程被硬编码为线性，无法承载「检索—验证—改写—再检索」这类 Agent 式多轮决策。
- **T｜任务**：从零设计一套可扩展的 Agent 编排内核，要求：新增能力零侵入、执行流程可替换、多模态数据契约统一。
- **A｜行动**：
  - **设计** 四层解耦架构：`Registry`（能力注册中心）→ `Strategy`（工作流编排）→ `Stage`（检索/重排/生成 ABC 契约）→ `Metric`（分阶段指标），任意组件通过 `@REGISTRY.register("name")` 声明式接入。
  - **抽象** `BaseStrategy` 编排层，落地 `LinearStrategy`（单轮线性）与 `IterativeStrategy`（多轮检索—充分性验证—查询改写循环，最大迭代轮次与充分性阈值可配，`_is_sufficient` / `_refine_query` 为子类留出决策钩子），使编排逻辑与工具实现彻底分离。
  - **重构** 数据契约层：用 Pydantic 定义 `ContentItem` 统一承载 text/image/video/pdf/audio 五种模态，引入 `parent_id / children_ids / level` 三级层级关系，一举解决文档级、页面级、句子级标注粒度不一致导致的指标口径错乱问题；`GroundTruth` 以 `eval_mode` 路由到检索/生成/选择题不同指标分支。
  - **构建** YAML 分层配置体系（`_base_` 继承 + 环境变量注入 + `--set` 命令行覆写），配置与代码解耦，离线环境可零改码切换模型路径。
- **R｜结果**：
  - 新增一个检索器/重排器的平均成本压缩到 **1 个文件 + 1 行装饰器**，累计零成本接入 **16 个检索器、7 个重排器、3 个生成器、13 个数据集加载器、24 个评测指标**。
  - 平台支撑 **279 组**跨模态实验稳定产出，覆盖 14 个公开基准；单个 MIRACL-VISION 多语言评测套件自动展开为 **120 份实验配置（18 语种 × 7 方法）** 一键批跑。

### 亮点二：主导分阶段缓存与断点续跑机制，将 Agent 长链路实验的迭代成本压缩一个数量级

- **S｜情境**：多模态索引构建极其昂贵——实测单次全量检索最长耗时 **89.2 小时**（finragbench_v + LCO-Embedding-Omni），中位数约 1 小时。而重排器选型需要在**同一份检索候选**上反复对比 7 款模型，若沿用「端到端整跑」模式，每次对比都要重复付出小时级甚至天级的索引与检索成本，且中途 OOM 或 API 限流即全盘作废。
- **T｜任务**：设计阶段级缓存与断点续评能力，让 Agent 流水线的任一阶段都能独立复跑、独立评测。
- **A｜行动**：
  - **设计** 基于内容寻址的 `EvalCache`：缓存 key = hash(阶段配置 + 数据集路径与变体 + 模型权重路径)，确保模型或数据一变即自动失效，绝不误用脏缓存。
  - **实现** `--stage retrieval / rerank / generation` 阶段解耦执行：重排阶段可从检索缓存直接取候选，或从 `results/*_retrieval_details.json` 反查 corpus 重建候选（合成 `1/rank` 分数保序），彻底摆脱对上游重跑的依赖。
  - **开发** 缓存自动发现机制（`--retrieval-method` 按方法名 + 数据集变体模糊匹配历史缓存），并在未命中时输出**可执行的补救指引**而非裸异常，显著降低协作者上手门槛。
  - **加固** 断点续评：`resume=True` 时按阶段跳过已完成计算，配合 OOM 容错（清缓存后继续而非中断）与失败样本落库 `EvalReport.errors`，保证天级任务不会因单点失败归零。
  - **建设** 可观测性：全链路 structlog 结构化日志 + 阶段延迟（P50/P95/P99）、token 消耗、API 成本三类性能指标随报告落盘。
- **R｜结果**：
  - 重排选型实验实现**一份检索候选服务 7 款重排器**，单次重排评测中位耗时降至 **64 分钟**、最快 **2.2 分钟**，相较端到端重跑（最长 89 小时）迭代效率提升 **1~2 个数量级**。
  - 232 次长周期检索任务全程零丢失重跑，天级任务可中断可恢复，GPU 资源利用率显著提升。

### 亮点三：搭建重排（Tool 层）能力矩阵与效果归因体系，实测重排使 nDCG@5 最高提升 33.4%

- **S｜情境**：多模态检索首轮召回精度有限，重排是提升端到端问答质量的关键环节；但业界重排模型形态割裂——逐文档打分（pointwise）、列表式生成（listwise）、视觉文档渲染、云端 API，接口与输入约束完全不同，缺乏统一横评手段导致选型只能靠猜。
- **T｜任务**：统一抽象重排能力，接入主流重排模型并给出可量化、可解释的选型结论。
- **A｜行动**：
  - **抽象** `BaseReranker` 统一契约，接入 **7 款异构重排器**（Qwen3-VL-Rerank 云端 API、Jina-Reranker-M0、LightOn-Rerank PW/LW 双形态、Nemotron-Rerank-VL、ZipRerank、RankZephyr listwise），把 pointwise/listwise/视觉渲染三类范式收敛到同一调用面。
  - **实现** 生产级鲁棒性设计：内置 `score_threshold` 分数阈值过滤低质候选；图像自动转 base64 Data URI 并按 `max_image_side` 缩放以压缩 token 开销；视频等不支持模态自动降级为文本回退或**垫底保序**，保证单点失败不污染整体排序；修复了原实现中 `min_similarity` 与重排分数口径混用的隐蔽缺陷。
  - **构建** 效果归因可视化体系：改造主可视化脚本优先读取 `metrics.rerank` 并回退 `metrics.retrieval`，新增 `visualize_rerank.py` 输出三类图表——逐实验前后分组柱状图（含 Δ 标注）、跨实验汇总对比图、**数据集 × 指标 Δ 热力图**（绿增红损，单元格标注「前→后」），让重排收益与负收益一眼可辨。
  - **完成** ZipRerank 早期剪枝（QI Early Pruner）等第三方模型的源码级适配与 8 套单元测试覆盖。
- **R｜结果**（基于 38 组重排前后对比实测数据）：
  - 重排整体带来 **nDCG@5 平均 +6.0%、MRR@10 平均 +5.7%**；最佳组合（e5-omni + Qwen3-VL-Rerank）在 LVBench 上 **nDCG@5 +33.4%（0.288→0.384）、MRR@10 +30.7%**，在 FinRAGBench-V 中文子集上 **MRR@10 +16.6%（0.714→0.832）**。
  - 通过热力图识别出重排在部分数据集造成 **-22.6%** 的负收益场景，据此输出「按数据集模态与候选集特征差异化启用重排」的选型结论，避免了盲目全量上线重排带来的效果回退风险。

### 亮点四：攻坚多模态模型与外部 API 的工程化疑难问题，保障 Agent 工具链高可用

- **S｜情境**：Agent 依赖的多模态模型与云端 API 是稳定性重灾区——本地模型遭遇框架版本不兼容导致的**静默错误**（指标异常但不报错）、大语料必然 OOM、多卡跨设备崩溃；云端 API 遭遇限流、编解码兼容性与体积硬限。任一环节失效都会让天级评测白跑。
- **T｜任务**：系统性定位并根治这些跨层问题，把工具链可用性从「碰运气」变为「可预期」。
- **A｜行动**：
  - **定位并修复静默 bug（最高难度）**：e5-omni 检索器出现 MMLongBench-Doc 指标近乎为 0 却无任何报错。通过「构造同分辨率图像对比余弦相似度」实验证实**图像嵌入完全塌缩（cos=1.0）**，逐层下钻锁定根因为 transformers 5.13.0 中 `prepare_inputs_for_generation` 错误预计算 M-RoPE position_ids；**移除该调用**改由模型依据 `image_grid_thw` 内部自算，修复后 GT 命中排名回到 `#1`、同文档页相似度回落至 0.857，指标全面恢复。并横向排查同架构的 jina、GVE 检索器，顺带修复 GVE 的 `_tied_weights_keys` 类型不兼容问题。
  - **治理显存瓶颈**：针对 Nemotron-ColEmbed 多向量 MaxSim「整库向量一次性上 GPU」的必然 OOM，**重构**为按 `score_chunk_size` 分块打分 + 全局零 padding（数学上与原实现严格等价），并额外提供 **float16 + numpy memmap 磁盘落盘**的低内存索引变体，配置完全隔离、不侵入原有路径，使超大语料在受限显存下可跑。
  - **重构并行方案**：诊断出 LCO-Embedding-Omni 使用 `device_map="auto"` 模型并行引发跨设备 bmm 崩溃（且模型单卡本可容纳），**重构为多进程数据并行**（每卡一份完整副本 + 分片编码 + 结果聚合），注入 `expandable_segments` 缓解显存碎片并增加 OOM 容错，2213 个视频索引构建**提速约 2 倍且不再静默跳过样本**。
  - **加固 API 工具调用链路**：实现 429 限流独立指数退避重试（退避次数与通用重试解耦）；针对 DashScope 服务端无法解码 VP9/AV1-in-MP4（抽样 30 个视频**失败率 73%**）的问题，量化对比多种方案后落地「**保持原分辨率重编码 H.264**」的 transcode 策略并前置到降级档序列首位，端到端验证 **4/4 视频全部编码成功**，同时省掉一次无效 API 往返、缩小上传体积与服务端 token 消耗；补齐 base64 20MiB 硬限适配（阈值调优覆盖 44 个原被误伤视频）。
- **R｜结果**：
  - 根治 1 个导致整批评测结果失效的**静默正确性 bug**，挽回 slidevqa / mmlongbench 等多个数据集的全部实验结论，并沉淀为团队级「多模态检索器上线前必做塌缩自检」规范。
  - 视频类工具调用失败率从 **73% 降至 0%**，多卡索引吞吐提升 **~2 倍**，OOM 类崩溃归零，天级评测任务可靠交付。

## 五、面试预演：高频追问与应答要点

1. **「IterativeStrategy 是否真跑通了多轮 Agent 决策？」**
   诚实回答：框架层（多轮循环、迭代上限、充分性阈值、`_is_sufficient` / `_refine_query` 钩子）已完整落地并可运行，但充分性判定当前是启发式实现，LLM-based 验证与查询改写留作子类扩展点——这正是我下一步希望在 Agent 岗深入的方向。
2. **「缓存 key 怎么保证不误用脏数据？」**
   key 由阶段配置 + 数据集路径与变体 + **模型权重路径**共同 hash；模型或数据集变体一变即自动失效，并在元数据中记录 pipeline 名与生成时间，加载时打印缓存年龄供人工复核。
3. **「图像塌缩 bug 是怎么发现的？」**
   关键在于**不信任「无报错」**：先用指标异常反推假设，再构造最小验证实验（同分辨率图像嵌入余弦相似度应 < 1，实测 = 1.0）把「猜测」变成「证据」，然后沿调用栈定位到位置编码预计算环节，修复后用 GT 排名与跨页相似度双指标交叉验证。
4. **「重排为什么会有负收益？」**
   重排器与首轮召回的模态适配度不一致：当候选集本身高度同质（如同一文档相邻页）或重排器不支持该模态而走了文本回退时，重排引入的噪声会超过收益——这也是我坚持做 Δ 热力图而非只报平均值的原因。
